## Context

Todo el catálogo (`FACT_TRACKS`, ~114k→1.6M filas) se alimenta hoy exclusivamente vía el pipeline de `ingesta`/`gestion_datos` (Airflow → Parquet → ClickHouse, recarga completa por semana). No existe ningún camino de escritura hacia `FACT_TRACKS` que no pase por ese pipeline batch. `creadores` introduce el primer camino de escritura *individual, síncrono, disparado desde FastAPI* hacia `FACT_TRACKS` — un patrón nuevo que convive con, pero no reemplaza, el pipeline batch existente.

El flujo tiene dos entidades con ciclo de vida propio y dos aprobaciones independientes:
1. **Cuenta de artista** (`DIM_CUENTA_ARTISTA`): un usuario autenticado solicita convertirse en artista (una sola vez); `admin` aprueba o rechaza esa cuenta completa.
2. **Track individual** (`FACT_SUBIDA_TRACK` + `STG_ARTIST_UPLOADS`): con cuenta aprobada, el artista sube tracks uno a uno; cada uno se revisa y aprueba/rechaza de forma independiente, sin relación con el estado de la cuenta una vez que esta ya está aprobada.

A diferencia de `STG_RAW_TRACKS` (efímera, se trunca tras cada carga batch), `STG_ARTIST_UPLOADS` es permanente: conserva el track crudo tanto si está pendiente, aprobado (ya promovido) o rechazado (nunca promovido) — es el registro de auditoría de qué subió cada artista, no solo un búfer de transformación.

## Goals / Non-Goals

**Goals:**
- Permitir que un usuario autenticado solicite una cuenta de artista y que `admin` la apruebe/rechace.
- Permitir que un artista con cuenta aprobada suba tracks (metadata real: nombre, álbum opcional, género existente, duración, explícito).
- Permitir que `admin` apruebe/rechace cada track de forma individual, con promoción real a `FACT_TRACKS` (`source_type='user_uploaded'`) al aprobar.
- Auditar ambas aprobaciones en `FACT_AUDIT_LOG` (reutilizando `paquetes.seguridad.audit.record`).
- Un artista ve solo su propia cuenta/subidas; `admin` ve todas (reutilizando `paquetes.seguridad.deps.require_admin`).

**Non-Goals:**
- Extracción real de features de audio (DSP) desde el archivo subido — no hay análisis de señal en este alcance. Los 13 atributos técnicos de audio (`danceability`...`valence`, `key`, `mode`, `time_signature`, `tempo`) se completan con valores neutros fijos al promover (ver Decisions), igual que el resto del modelo técnico ya acepta valores derivados/calculados y no "escuchados".
- Almacenamiento del archivo de audio en sí (upload de binario, storage de objetos) — esta capability registra la *metadata* del track subido; el archivo de audio queda fuera de alcance (podría vivir en PocketBase como campo de archivo en una capability futura).
- Re-solicitud de cuenta de artista tras un rechazo — cada usuario tiene como máximo una fila en `DIM_CUENTA_ARTISTA`; reabrir una cuenta rechazada queda fuera de alcance.
- Edición o eliminación de un track ya subido/revisado — el flujo es unidireccional (subir → revisar → promover o quedar rechazado).
- Rediseñar el pipeline de `ingesta`/Airflow o su estrategia de `fact_id` — solo se aplica el cambio mínimo y contenido descrito en Decisions ("Preservación de tracks `user_uploaded` frente a una recarga completa") para que la recarga completa no borre tracks promovidos; no se toca ninguna otra parte del pipeline batch.

## Decisions

### `DIM_CUENTA_ARTISTA` vive en ClickHouse (no en PocketBase), igual que `DIM_USUARIO`
La cuenta de artista es un dato operativo con ciclo de vida propio (pendiente → aprobada/rechazada) que se audita y se consulta analíticamente (ej. cuántas cuentas se solicitan por semana). Sigue el mismo precedente ya aceptado en `seguridad` para `DIM_USUARIO`/`FACT_SESION`: excepción deliberada a RT-05 para datos operativos/transaccionales, con `ReplacingMergeTree(actualizado_en)` para reflejar la transición de estado sin duplicar filas. Alternativa descartada: modelarla como colección de PocketBase — se rechaza para no fragmentar el estado de aprobación entre dos bases de datos cuando ya existe el patrón establecido de `DIM_USUARIO` para esto mismo.

### `FACT_SUBIDA_TRACK` también usa `ReplacingMergeTree`, mismo patrón que `FACT_SESION`
Cada subida nace `pendiente` y se resuelve una sola vez (aprobado/rechazado) — apertura/cierre, igual que una sesión. Se versiona con una columna `version` (bump en la resolución) y `ORDER BY subida_id`, reutilizando exactamente el patrón ya documentado para `FACT_SESION` en `seguridad` en vez de inventar uno nuevo.

### `STG_ARTIST_UPLOADS` es append-only y permanente — no se trunca nunca
A diferencia de `STG_RAW_TRACKS` (efímera, ligada al pipeline batch), esta tabla es el registro crudo de cada subida de artista y debe sobrevivir indefinidamente (es la fuente de verdad de "qué subió el artista", tanto para tracks aprobados como rechazados). El estado de revisión no vive aquí, sino en `FACT_SUBIDA_TRACK.estado_revision_id` — evita duplicar el estado en dos tablas.

### `DIM_ESTADO_REVISION` como catálogo pequeño de 3 filas, mismo patrón que `DIM_EXPLICIT_TYPE`
`pendiente`/`aprobado`/`rechazado`, sembrado una vez al iniciar (igual que `DIM_MUSICAL_KEY`, `DIM_MODE`, etc. en `etl/gold/loader.py`). Se aplica únicamente al track individual — independiente del estado de la cuenta, tal como pide el enunciado.

### El `usuario_id`/`cuenta_artista_id` de escritura siempre se deriva del token, nunca del body
La solicitud de cuenta y la subida de un track obtienen su identidad exclusivamente de `core.deps.get_current_user`, igual que ya hace `facturacion`. Ningún endpoint de escritura acepta un `usuario_id` o `cuenta_artista_id` ajeno en el body.

### Solo una cuenta de artista aprobada por usuario habilita la subida
Antes de aceptar un track, el endpoint de subida resuelve `DIM_CUENTA_ARTISTA` del usuario autenticado (vía `argMax(estado_cuenta, actualizado_en)` sobre `usuario_id`) y exige `estado_cuenta='aprobada'`; de lo contrario, 403. Esto es una dependencia propia de `creadores` (`require_cuenta_artista_aprobada`), análoga a `require_suscripcion_activa` de `facturacion`.

### Promoción a `FACT_TRACKS`: función Python síncrona dentro del endpoint de aprobación de track, no un DAG de Airflow
Al aprobar un track individual, el propio endpoint de FastAPI (no Airflow) ejecuta la promoción: resuelve/crea `artist_id` en `DIM_ARTISTS` (busca por `name=nombre_artistico`; si no existe, inserta con `artist_type='Independiente'`), resuelve/crea `album_id` en `DIM_ALBUMS` (usa `track_name` como álbum tipo `Single` si no se especificó álbum), usa el `genre_id` ya elegido por el artista de la lista existente de `DIM_GENRES`, y usa el `date_id` más reciente de `DIM_DATE` como fecha de carga. Los 13 atributos de audio se completan con valores neutros fijos (`key=0`, `mode=1`, `time_signature=4`, `tempo=120.0`, `energy=0.5`, `danceability=0.5`, `loudness=-10.0`, `speechiness=0.05`, `acousticness=0.3`, `instrumentalness=0.0`, `liveness=0.1`, `valence=0.5`, `popularity=0`) y sus IDs derivados (`popularity_range_id`, `tempo_range_id`, `energy_level_id`, `key_id`, `mode_id`, `time_signature_id`, `explicit_id`) se calculan con las mismas fórmulas/umbrales ya usados en `etl/gold/loader.py` (`_TS_MAP`, cortes de `popularity`/`tempo`/`energy`), para no introducir un segundo criterio de bucketing. El nuevo `fact_id` se asigna como `max(GREATEST(fact_id, FACT_ID_FLOOR_USER_UPLOADED - 1)) + 1` bajo un `asyncio.Lock` propio del router de `creadores` (mismo patrón que `_trigger_lock` en `gestion_datos`) — ver la constante `FACT_ID_FLOOR_USER_UPLOADED` en la siguiente decisión — suficiente para el volumen de aprobaciones manuales de `admin` (no hay alta concurrencia esperada en este flujo). Alternativa descartada: reutilizar el DAG de Airflow para la promoción — se rechaza porque el DAG está diseñado para recarga completa por semana, no para insertar una fila puntual on-demand; forzar ese flujo agregaría latencia (disparo async + polling) sin beneficio, y RT-01 solo exige que el movimiento ocurra "desde Python", no específicamente desde Airflow.

### `analitica` excluye `source_type='user_uploaded'` de sus promedios de atributos de audio, no de conteos ni de popularidad
Los 13 atributos de audio de un track promovido son valores neutros fijos, no mediciones (ver Non-Goals). Sin exclusión, cualquier `avg(energy)`/`avg(danceability)`/etc. agrupado por género o por artista en `analitica` se sesga hacia esos valores constantes — el efecto es despreciable a nivel de catálogo completo (~1.6M filas), pero significativo exactamente donde `analitica` hace benchmarking real: un artista nuevo cuyo catálogo es 100% `user_uploaded` mostraría un "perfil de audio" que en realidad es puro relleno, presentado a un Cliente B2B como si fuera señal real; un género con pocos tracks tiene el mismo problema. Se excluyen específicamente en las consultas que realmente están montadas en `analitica/router.py` (`DASHBOARD_KPIS`, `GENRE_AUDIO_PROFILE_V1`, `ARTIST_AUDIO_STATS_V1`, `TENDENCIAS_LOAD_WEEK`, y la legacy `DASHBOARD_AUDIO_AVG` que sigue sirviendo el dashboard) usando `avgIf(columna, source_type != 'user_uploaded')` en vez de `avg(columna)`, columna por columna — sin agregar una cláusula `WHERE` global, porque `track_count`/`avg_popularity`/`explicit_count` de esas mismas consultas SHALL seguir incluyendo todos los tracks (son hechos reales: cuántos tracks tiene un artista/género, y su popularidad real —incluida la de un track nuevo con `popularity=0`—, no dependen de análisis de audio). Esto modifica el comportamiento observable de 5 requirements ya especificados en `analitica` (`Dashboard ejecutivo de KPIs`, `Perfil de audio por género`, `Comparación lado a lado de dos artistas`, `Benchmark de artista contra su género`, `Tendencias temporales por semana`) — de ahí el delta `MODIFIED Requirements` en `specs/analitica/spec.md`. La excepción es deliberada frente al requirement ya existente "el benchmark de género SHALL calcularse... sin excluir outliers": esa cláusula existe para no descartar mediciones reales incómodas, no para forzar valores fabricados dentro de un promedio — se aclara explícitamente en el texto modificado que la exclusión de `user_uploaded` no es una exclusión de outliers. Las consultas de `analitica/queries.py` que no están montadas en ningún router (`GENRES_TRENDS`, `GENRE_AUDIO_PROFILE`, `TRENDS_WEEKLY`, `ARTIST_STATS`, `ARTIST_GENRE_BENCHMARKS`) son código muerto preexistente y no se tocan. Alternativa descartada: excluir el track `user_uploaded` por completo (de conteos y popularidad también) — se rechaza porque esos sí son hechos reales del negocio (el track existe, tiene 0 streams porque es nuevo), y ocultarlos distorsionaría igual de mal en la dirección contraria.

### Promoción también fija `load_week`, no solo `date_id`
`FACT_TRACKS.load_week` es una columna separada de `date_id` (aunque hoy numéricamente coinciden en el pipeline batch: `run_gold`/`run_synthetic` insertan `date_id = load_week = número de semana`). La promoción de `creadores` fija ambas al mismo valor (`max(load_week)` vigente en `FACT_TRACKS`), para no dejar `load_week` en un valor por defecto inconsistente que rompería el agrupamiento de `TENDENCIAS_LOAD_WEEK` (serie temporal por semana de `analitica`) — un track publicado por un artista queda agrupado en la semana "actual", igual que asignaría el pipeline batch si cargara datos ese mismo día.

### Preservación de tracks `user_uploaded` frente a una recarga completa de `ingesta`
El pipeline batch (`_truncate_fact_tables` en `gestion_datos`, invocada por `/etl/clear` y por cada disparo de `ingesta`) hoy hace `TRUNCATE TABLE FACT_TRACKS` sin condición — un `admin` que dispara una recarga completa borraría también los tracks ya aprobados por `creadores`, que es pérdida de datos real, no una staleness aceptable como la de `FACT_ENGAGEMENT_USUARIO`/favoritos (un favorito referencia un `fact_id` que puede volver a existir tras la recarga; un track `user_uploaded` borrado no vuelve a existir en ningún lado — su única fuente era la propia aprobación). Se aplica una salvaguarda mínima y contenida, sin rediseñar el pipeline batch:
1. **`fact_id` reservado para `user_uploaded`**: la promoción en `creadores` asigna `fact_id` a partir de una constante `FACT_ID_FLOOR_USER_UPLOADED = 10_000_000` (muy por encima del techo documentado de `FACT_TRACKS`, ~1.6M filas al final del semestre), de modo que nunca colisiona con el rango de `fact_id` que asignan `run_gold`/`run_synthetic` (1..~1.6M) — sin importar el orden en que se ejecuten las dos escrituras.
2. **`_truncate_fact_tables` (en `gestion_datos`) deja de vaciar `FACT_TRACKS` sin condición**: para esa tabla específicamente, el `TRUNCATE TABLE FACT_TRACKS` se reemplaza por `ALTER TABLE FACT_TRACKS DELETE WHERE source_type != 'user_uploaded'` (mutación — mismo mecanismo ya usado por `dim_delete` en el propio `gestion_datos`), que borra todo lo que la recarga batch va a regenerar y conserva intactas las filas `user_uploaded`. `ETL_BATCH_CONTROL` sigue truncándose igual que hoy (no tiene relación con `creadores`).

Esto es un cambio pequeño y autocontenido (una constante en `creadores` + una línea de SQL en una función ya existente de `gestion_datos`), no una migración del pipeline batch: `run_gold`/`run_synthetic` no se tocan, siguen asignando `fact_id` desde 1 exactamente igual que hoy. Alternativa descartada: copiar las filas `user_uploaded` a una tabla temporal antes del truncado y reinsertarlas después — se rechaza por ser más código y más superficie de fallo (dos pasos adicionales, ventana de inconsistencia) para el mismo resultado que ya logra una única sentencia `DELETE WHERE`.

### `FACT_TRACKS.is_synthetic` se reemplaza por `source_type` (no conviven ambos campos)
Decisión ya registrada en `docs/decisiones-refactorizacion.md` (sección 7), ejecutada en este cambio porque es el primero que vuelve a tocar `FACT_TRACKS` desde una capability de negocio: `is_synthetic Bool` se reemplaza por `source_type Enum8('real'=1, 'synthetic'=2, 'user_uploaded'=3)` (los dos primeros valores cubren exactamente los dos orígenes que ya existían bajo `is_synthetic=false/true`; el tercero es el que introduce `creadores`). Se rechaza mantener ambos campos en paralelo porque duplicaría la misma información en dos formas y arriesgaría que uno se actualice y el otro no (ya descartado explícitamente en el log de decisiones). Se aplica como una migración de esquema (recrear la columna) más el renombre mecánico de todo lector/escritor existente de `is_synthetic` sobre `FACT_TRACKS`, sin cambiar el comportamiento observable de ningún endpoint:
  - `api/paquetes/catalogo/queries.py` (`TRACKS_TOP`, `TRACKS_BY_ARTIST`): `is_synthetic = 0` → `source_type != 'synthetic'` (equivalente: incluye `real` y, de ahora en adelante, `user_uploaded` — un track de artista aprobado debe poder aparecer en el catálogo navegable, que es el propósito de esta capability).
  - `api/paquetes/biblioteca/queries.py` (`FAVORITOS_ACTUALES`, `HISTORIAL_RECIENTE`): mismo reemplazo `is_synthetic = 0` → `source_type != 'synthetic'`.
  - `api/paquetes/gestion_datos/queries.py` (`facts_list_sql`, `DATA_QUALITY_COUNTS`): la columna expuesta pasa a `source_type`; `DATA_QUALITY_COUNTS` pasa a `countIf(source_type = 'real')` / `countIf(source_type = 'synthetic')` y suma `countIf(source_type = 'user_uploaded') AS user_uploaded_records` (el endpoint `GET /data-quality` de `gestion_datos` expone el nuevo conteo junto a los existentes, sin quitar ninguno).
  - `etl/gold/loader.py` y `etl/gold/synthetic.py`: escriben `source_type='real'` / `source_type='synthetic'` respectivamente en vez de `is_synthetic=False`/`True`.
  - **No se toca** `FACT_ENGAGEMENT_USUARIO.is_synthetic` (columna homónima pero de otra tabla, con otro significado — marca si un evento de engagement es simulado — fuera del alcance de esta decisión, que es exclusiva de `FACT_TRACKS`).
  Alternativa descartada: agregar `source_type` como columna aditiva y dejar `is_synthetic` intacto — se rechaza explícitamente por ser la opción ya descartada en el log de decisiones del proyecto (redundancia de información, riesgo de inconsistencia).

### Una sola tabla `FACT_TRACKS`, no una tabla paralela para uploads de artista
El track promovido se inserta directamente en `FACT_TRACKS` (marcado `source_type='user_uploaded'`), no en una tabla separada tipo `FACT_TRACKS_USUARIO`. Alternativa descartada: tabla paralela — se rechaza porque fragmentaría cualquier consulta de catálogo/analítica que ya asume una única `FACT_TRACKS` (rompería `catalogo`, `analitica` sin necesidad).

### Auditoría y autorización 100% reutilizadas de `seguridad`
Tanto la resolución de cuenta como la de track (aprobar/rechazar) llaman a `paquetes.seguridad.audit.record(...)`, y ambos endpoints administrativos usan `Depends(require_admin)` importado de `paquetes.seguridad.deps` — ningún mecanismo propio nuevo, siguiendo el mismo precedente que `facturacion`.

### Lectura: propio vs. admin, mismo patrón de query param opcional que `facturacion`
`GET /cuenta` y `GET /subidas` sin parámetro devuelven los datos del usuario autenticado; `admin` puede pasar `usuario_id`/`cuenta_artista_id` para consultar cualquier artista (gateado por `require_admin`, igual que `_resolver_usuario_objetivo` en `facturacion`). `admin` además tiene un listado propio de pendientes (`GET /admin/cuentas?estado=pendiente`, `GET /admin/subidas?estado=pendiente`) para la cola de revisión.

## Risks / Trade-offs

- [Riesgo] Sin salvaguarda, el pipeline de `ingesta` truncaría `FACT_TRACKS` por completo en cada recarga (`_truncate_fact_tables` en `gestion_datos`), borrando también los tracks promovidos por `creadores` — pérdida de datos real, no staleness recuperable (a diferencia de favoritos/historial, que solo referencian un `fact_id` que puede resolver a otra fila tras la recarga). → Mitigación implementada en este cambio (ver Decisions, "Preservación de tracks `user_uploaded`"): `_truncate_fact_tables` pasa de `TRUNCATE` a `ALTER TABLE FACT_TRACKS DELETE WHERE source_type != 'user_uploaded'`, y la promoción usa un rango de `fact_id` reservado (`>= 10_000_000`) que nunca colisiona con el rango del pipeline batch. Riesgo residual aceptado: el `DELETE` es una mutación asíncrona en ClickHouse (no instantánea) — durante la ventana de la mutación, una consulta podría ver brevemente filas que ya deberían estar borradas; se acepta porque el disparo de una recarga completa es una acción manual y poco frecuente de `admin`, no una operación en el camino caliente de usuarios.
- [Riesgo] `fact_id` bajo un lock de proceso único no protege contra múltiples instancias de la API corriendo en paralelo (fuera del caso actual de un solo worker `uvicorn`, ver `api_Dockerfile`). → Mitigación: aceptado, mismo supuesto de un solo worker que ya asume `_trigger_lock` en `gestion_datos`.
- [Riesgo] Los valores neutros fijos de audio features no reflejan el sonido real del track. → Mitigación implementada en este cambio (ver Decisions, "`analitica` excluye `source_type='user_uploaded'`..."): los promedios de atributos de audio de `analitica` excluyen estos tracks; conteos y popularidad no cambian. Riesgo residual aceptado: cualquier consulta *fuera* de `analitica` que calcule su propio promedio de audio sobre `FACT_TRACKS` sin pasar por las queries ya corregidas (hoy no existe ninguna fuera de `analitica`/ETL) heredaría el mismo sesgo si se agrega en el futuro sin replicar este criterio.
- [Riesgo] Un artista con nombre artístico igual (colisión de texto) a un `artist_id` ya existente en `DIM_ARTISTS` del dataset base se fusiona con esa entidad. → Mitigación: aceptado; el match por nombre exacto es el mismo criterio ya usado por el pipeline batch (`load_lookup` en `etl/gold/loader.py`) para resolver `artist_id`/`album_id`/`genre_id`.

## Migration Plan

Se agregan las 4 tablas nuevas (`DIM_CUENTA_ARTISTA`, `FACT_SUBIDA_TRACK`, `DIM_ESTADO_REVISION`, `STG_ARTIST_UPLOADS`) a `init_clickhouse.py` (idempotente, `CREATE TABLE IF NOT EXISTS`). `DIM_ESTADO_REVISION` se siembra una vez (3 filas) al iniciar, igual que las demás dimensiones pequeñas. El paquete `api/paquetes/creadores/` se monta en `main.py`.

`FACT_TRACKS` ya tiene datos reales cargados en el ClickHouse de desarrollo (varias semanas ya ejecutadas), así que el cambio `is_synthetic`→`source_type` sí necesita backfill, en dos partes:
1. La `CREATE TABLE IF NOT EXISTS FACT_TRACKS` en `init_clickhouse.py` se edita para definir `source_type Enum8('real'=1, 'synthetic'=2, 'user_uploaded'=3)` en vez de `is_synthetic Bool` — rige para instalaciones nuevas (`CREATE TABLE IF NOT EXISTS` no altera una tabla ya existente).
2. Para el ClickHouse de desarrollo ya desplegado, se ejecuta una sola vez (no como parte del arranque idempotente): `ALTER TABLE FACT_TRACKS ADD COLUMN source_type Enum8('real'=1,'synthetic'=2,'user_uploaded'=3) DEFAULT 'real'`, luego `ALTER TABLE FACT_TRACKS UPDATE source_type = 'synthetic' WHERE is_synthetic = 1` (mutación, mismo mecanismo ya usado por `dim_delete` en `gestion_datos`), y finalmente `ALTER TABLE FACT_TRACKS DROP COLUMN is_synthetic`. Se documenta como paso manual de esta ronda (igual que "verificar con curl real"), no se agrega a `DDL_STATEMENTS` porque no es re-ejecutable de forma idempotente una vez que `is_synthetic` ya no existe.

No hay backfill de datos previos para las 4 tablas nuevas: no existe historial de cuentas/subidas antes de este cambio. Despliegue vía `docker compose up`, sin pasos manuales adicionales salvo el backfill de `source_type` descrito arriba (ejecutado una única vez).

## Open Questions

- Si en el futuro se agrega almacenamiento real de archivo de audio, `STG_ARTIST_UPLOADS` necesitará un campo de referencia (ej. URL/path) — hoy fuera de alcance.
